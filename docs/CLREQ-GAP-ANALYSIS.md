## 0. 摘要

- **clreq 与本项目的定位存在部分错位**：clreq 明确写道「至于古籍排版，非本文件所及」，
  而本项目的主战场（`ltc-guji`、句读、夹注、眉批、版心鱼尾）恰恰是古籍。因此
  「完整 CLReq 实现」的收益主要落在 **`ltc-cn-vbook` / `ltc-tw-vbook` 两个现代竖排文档类**上，
  古籍类只需保证不冲突。
- **当前覆盖率（估算）**：以「只做直排」为口径，clreq 条款覆盖约 **45%–50%**；
  若把横排条款也计入分母，约 **25%–30%**。页面版式（版心/行长/行数/行距/分栏）覆盖最好（约 70%），
  行内调整（挤压/拉伸优先顺序）覆盖最差（约 20%，基本缺位）。
- **最大的单点缺口不是功能，而是模型**：clreq 的行内调整要求「每个间隙带有可挤压/可拉伸量与优先级」，
  而当前 `layout-grid` 的 grid 模式是**刚性等距格**，natural 模式是**整列均分间隙**，两者都没有
  「可调空间链 + 优先级求解」这一层。标点挤压、禁则的「先挤进后推出」、中西间距、均排、
  纵横对齐全部依赖它。**这一层是整个工程的地基，必须先建**——且先在横排场地建
  （共享内核 H0，见 `docs/CLREQ-HORIZONTAL-PLAN.md`），竖排随后接线。
- **实施策略：横排先行、共享内核回流竖排**。横排可直接复用 TeX 断行器
  （禁则=penalty、可调空间=glue），同一条 clreq 条款的实现成本约为竖排的 1/3，
  是验证共享规则内核的最低成本场地。横排 H0–H6 约 **100 人日**，
  竖排回流 P1–P5/P7 约 **93 人日**，合计期望 **193 人日**（≈10 人月，乐观 152 / 悲观 248）。
  首个可对外宣称的里程碑（H0+H1+H2，横排标点与禁则达标）约 **46 人日**。
- **建议口径**：不追求 100%，而是发布一份 **《clreq 符合度声明矩阵》**，逐条标注
  「实现 / 部分实现 / 不适用 / 不实现（并说明理由）」，并把 H0–H2 作为第一个里程碑。

## 1. 依据与方法

1. 抓取 clreq 全文，按 `lang="zh-hans"` 过滤出简体中文正文，得到约 4.6 万字的条款文本。
2. 按 clreq 的章节结构（文本方向 / 字形 / 排版单元 / 标点与行内 / 行与段落 / 页面与书籍 / 标点表）
   逐节抽取「可实现的排版要求」，剔除纯背景叙述。
3. 对每条要求在本仓库中定位实现证据（文件:行），标注状态：
   ✅ 已实现　🟡 部分实现　❌ 未实现　➖ 不适用（横排专属或非排版引擎职责）。

## 2. 范围界定：三种「完整实现」口径

| 口径 | 含义 | 是否推荐 |
|------|------|----------|
| **A. 直排子集** | 实现 clreq 中所有与直排相关的条款；横排条款标注「不适用，交由生态其他包」 | 不推荐：省不了共享内核的工作量，却少一个横排产品 |
| **B. 直排 + 横排注音** | A 之外，为汉语拼音标音单独实现一个横排的注音行（clreq 的罗马拼音标音仅横排） | 不推荐：同上 |
| **C. 全覆盖** | 横排与直排两条后端，共享同一套 clreq 规则内核 | ✅ **采用** |

口径 C 的实施路径是**横排先行**（`docs/CLREQ-HORIZONTAL-PLAN.md`，H0–H6）：
横排可直接用 TeX 的断行器作为求解器（同一条 clreq 条款的实现成本约为竖排的 1/3），
且真正需要共享的是「带优先级的一维空间分配器」这个纯函数，横排是验证它的最低成本场地。
共享内核（标点表 / 空间分配器 / 禁则）在横排阶段 H0 建成并验证后回流竖排。

下文第 4 节按 clreq 章节分析差距（横竖排通用）；第 6 节的 P1–P5/P7 描述**竖排后端**
在共享内核建成之后要补的条款，工作量已按复用折算（原 P0 已并入 H0，原 P6 即横排规划本身）。

## 4. 详细差距分析

### 4.1 标点符号系统（`tex/core/luatex-cn-core-punct.lua`）

**已有能力**

- 6 类分类 `CL_OPEN / CL_CLOSE / CL_FULLSTOP / CL_COMMA / CL_MIDDLE / CL_NOBREAK`
  （`luatex-cn-core-punct.lua:137-206`）。
- 直排字形替换表 `VERT_FORM_MAP`，含括号类、引号类、`—`、`…`（同上 `:212-242`）；
  字体缺字时对 `—`/`…` 退化为旋转（`:572-576`）。
- 字体缺乏标准码位（`vert` GSUB 落到 PUA）时，通过 `tounicode` 反查还原（`:264-302`）。
- 标点字面墨心测量与补偿（`:65-129`），这是实现「字面始端 / 字面居中」两种字面分布的良好基础。
- 大陆式偏靠偏移 `MAINLAND_OFFSETS`（`:766-772`）。

**关键差距**

1. ~~**挤压是无条件的**~~ → **已解决一半（#132）**。`squeeze-mode = context` 下
   只有「① 连续标点相邻」触发，夹在汉字之间的单个标点占满一字幅；规则在
   `tex/shared/luatex-cn-punct-squeeze.lua`，横竖排共用。
   **「② 标点位于行首/行尾」仍未实现**——断列结果在 flatten 阶段还不知道，
   要等 P2 接线（设计见 `CLREQ-VERTICAL-ADJUST-DESIGN.md` §2.3）。
   按 R5 分档：`ltc-guji` 默认仍是 `legacy` 无条件挤压。
2. ~~**缺少「相邻两标点占 1.5 字宽」规则**~~ → **已解决（#132）**。
   2 → 1.5 字宽为默认，`adjacent-punct=1` 可收到 1 字宽；挤压方向按
   「空白在哪一侧就往哪边让」，夹注符号紧贴被夹注内容。
3. **缺少大量标点类别**：连接号（`–`/`～`）、间隔号（`·`，港台占一字、大陆占半字）、
   分隔号（`/`）、破折号与省略号的**两字宽整体单元**、叹问号叠加（`?!`/`!?`/`???`）。
   **叹问号叠加另需专门处理**（横排 H0/H1 也未做）：`？？` `！！` 之外，
   **`？！` `！？` 这类异字组合同样是一个两字幅整体**，须与 `——` `……`
   同样按刚性单元对待——内部不挤压、不拆行、不被兜底均分撑开。
   现行共享层只认预组合码位 `‼`(U+203C) `⁇`(U+2047)，序列形式不识别；
   `is_unbreakable_pair` 又限定 `a == b` 且类别为 dash/ellipsis，
   两条都挡住了叠加符号。断行侧因两符号都属行首禁则而侥幸不拆，
   但宽度侧会被当作普通连续点号挤压，是错的。
4. **`CL_NOBREAK` 名不副实**：定义了却没有任何「不可拆成两行」的执行逻辑。
5. **偏移量是经验值**（`x=0.20, y=0.25`），而非按 clreq 的「字面始端」定义 + 字体度量推导。
   墨心测量基础设施已有（#134 又补了 `helpers.glyph_ink_span`，按
   `descriptions.boundingbox` 取真实墨迹盒），应改为度量驱动。
   **这一条同时能解掉两个已观察到的现象**：京華老宋体下逗号前后都留白
   （偏靠量与该字体的字面分布不匹配）、括号按墨迹居中而汉字按 em 框居中
   的不一致。代价是会重排所有大陆式竖排版面，基线要整体重存一次。

### 4.2 换行禁则与行内调整（最大缺口）

**已有能力**

- grid 模式的 kinsoku 钩子：向前看一个字符，若下一字符禁止行首则把当前字符一起推到下一列；
  若当前字符禁止行尾也推出（`luatex-cn-core-punct.lua:399-486`）。
- natural 模式的 kinsoku：比较「挤进」与「推出」两种方案的每间隙代价，取代价小者
  （`layout-grid.lua:1552-1626`）。这是最接近 clreq「先挤进，后推出」的一处实现。

**关键差距**

1. **禁则级别不可配置**。clreq 定义四级（不处理 / 基本处理 / GB 法 / 严格处理），
   现在硬编码为「基本处理」的子集：行首禁止 `close/fullstop/comma/middle`、
   行尾禁止 `open`（`punct.lua:340-352`、`layout-grid.lua:1544-1550`）。
   缺连接号/间隔号/分隔号的行首禁止、缺分隔号的行尾禁止、缺严格级的破折号/省略号行首禁止。
2. **符号分离禁则整体缺失**：两字宽标点不得拆列、阿拉伯数字整体不拆、
   `数字+%/‰/°/℃`、`+/-/± + 数字`、货币符号 + 数字、上下标与注释记号不得与被标记文字分离。
3. **行尾点号悬挂未实现**，代码里有明确的 TODO（`punct.lua:669-671`）。
   clreq 指出悬挂**适用于直排**（横排港台式因点号居中不宜悬挂），正是本项目的主场。
4. **没有挤压/拉伸优先级引擎**。clreq 的挤压顺序为：
   行末标点 → 西文词距 → 间隔号 → 夹注符号 → 逗号/顿号/分号 → 中西间距 → 句号/问号/叹号；
   拉伸顺序为：西文词距 → 中西间距 → 兜底均分（且禁止拉伸不可分离单元、避免拉伸连接号/分隔号两侧）。
   grid 模式完全没有这一层；natural 模式只有「整列 gap 均分」。
5. **均排（justify）缺失**：`vertical-align` 只有 top（默认）/center/bottom
   （键定义在 `luatex-cn-core-content.sty:129-130`，取值校验在
   `luatex-cn-layout-grid.lua:542`），没有把余量平均分配到字间的模式。

### 4.3 中西文混排

clreq 要求直排下西文有三种配置：等宽/全角直立、顺时针旋转 90°、以及缩略词整体入格；
横排下汉字与西文之间加不超过 1/4 汉字宽的间距，且中西间距参与行内调整（可挤到 1/8、拉到 1/2）；
纵横对齐时西文所占空间应为汉字的整数倍。

现状：引擎按字形逐个放入格子，`cell_height` 取字号（`layout-grid-helpers.lua:270-298`），
比例西文字母会各占一格且横向不居中；`ATTR_VERT_ROTATE` 只在标点缺字时使用
（`render-page-process.lua:137-140` 有完整的旋转 + 平移实现，**可复用**）；
没有任何中西间距插入逻辑。`\填充文本框` 可以手工模拟「中横排」，但不是自动机制。

### 4.4 行间注与注音

- **行间批语**：本项目的 `\侧批`/`\夹注`/`\眉批` 体系成熟，覆盖 clreq「行间批语位基文左侧、
  长度不拘、可换色」的要求，甚至超出。
- **注音符号（ㄅㄆㄇ）标音**：完全缺失。clreq 给了非常具体的度量：注文占基字**一半**空间、
  单符号与基字比 **3:10**、平上去调号在末符号右上方（直式向上回返半个符号空间）、
  入声调号在整体外侧右下、轻声在字音前方且高度与基字比 **1:15**、
  直排时注文整体垂直居中于基字、注音不得单独出现在行首。
  这一块**规范最细、最可测试**，对 `ltc-tw-vbook` 价值最高。
- **罗马拼音标音 / 中外文对照 / 词对齐**：仅横排，由横排规划 H4 实现。

### 4.5 页面与书籍版式

- 版心（type area）设计要素（字号、行长、行数、行距、栏数、栏距、版心相对成品尺寸的位置）
  基本齐备，band 分栏可对应 clreq 的「分栏」。**术语提醒**：clreq 的「版心」= type area，
  与本项目中「版心」= 书页中缝（鱼尾/象鼻）不是一回事，文档中需要显式消歧。
- **孤行孤字完全没有处理**（全仓库无 widow/orphan 相关代码）。clreq 给出的处理手段
  （从前行借一字并对该行均排）依赖 4.2 的均排能力。
- 标题处理：缺「占行」（标题占基本版式的整数倍行数）、「单页起」（奇偶页起）、
  「同行标题」（标题与正文同列、间隔一个全角空白）、「跨栏标题」。
- 号数 ↔ 点数换算表（初号 42pt … 七号 5.25pt）可以直接做成字号别名，成本极低、体验收益明显。

## 5. 架构前提与风险

| # | 风险 | 说明 | 应对 |
|---|------|------|------|
| R1 | **刚性网格 vs 弹性调整** | clreq 的行内调整本质是「带优先级的可调空间链」，与固定格模型冲突 | 求解器在 H0（`shared/adjust.lua`）建成并经横排验证；P2 在竖排引入 `cell = {size, shrink, stretch, priority}` 模型接线，grid 模式退化为 shrink=stretch=0 的特例 |
| R2 | **grid / natural 双轨制** | 同一规则要写两遍（现在 kinsoku、标点挤压都已经各写了一份），长期必然发散 | P2 统一到 H0 的共享求解器，两种模式只是参数差异 |
| R3 | **像素回归测不出规范符合性** | 若 bug 已进基线，`regression_test.py` 无法发现 | 扩展 `test/geometry_test.py` 思路，建 **clreq 断言测试**：解析 PDF 内容流，直接断言「逗号占半格」「注音符号与基字比 3:10」等度量 |
| R4 | **字体依赖** | 注音符号、`vert` 特性、波浪线字形都依赖字体支持 | 在 `scripts/download_fonts.py` 的 manifest 中固定一套含注音符号的测试字体；缺字时给出明确 warning 而非静默降级 |
| R5 | **古籍类回归** | 标点挤压规则改为「上下文相关」会改变现有古籍示例的版面 | 规则按文档类分档：`ltc-guji` 保持现状为默认，新规则在 vbook 类启用；每一步都跑 basic/past_issue/complete 三套基线 |
| R6 | **规范本身的可选性** | clreq 大量条款是「排版风格」而非强制（如是否挤压、禁则级别） | 所有新规则都做成可配置键，并提供 `大陆`/`台湾`/`不调整` 三套预设 |

   是后续所有阶段的验收基座，不要跳过它直接改 `punct.lua`
   （具体第一步见横排规划第 8 节：先出 `ai_must_read/clreq-shared-core.md` 接口契约）。
3. **按文档类分档启用**：新规则默认只在横排包与 `ltc-cn-vbook` / `ltc-tw-vbook` 生效，
   `ltc-guji` 通过显式开关选用。古籍复刻的既有版面不应因为「更符合现代规范」而改变。
4. **不追求 100%，追求可核查**：发布符合度矩阵，把「不实现」也写清楚理由
   （bidi 非本引擎职责、儿化小字用字罕见等）。这比模糊地宣称「支持 clreq」更有价值。
5. **优先级排序建议**：禁则与悬挂（用户最易感知）> 标点宽度调整（版面质量）>
   中西混排（实际文档高频）> 注音（`ltc-tw-vbook` 差异化卖点）> 孤行孤字（长尾）。
6. **把 P2（竖排接线）单独立项评审**：它会触及 `layout-grid.lua`（2700 行）的核心路径，
   建议在共享内核接口契约之外，再出一份竖排 cell 模型与接线方案的设计文档，评审后动手。
